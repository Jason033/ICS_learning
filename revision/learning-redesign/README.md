# 學習產品重新設計：目標與教學方向草案

更新日期：2026-10-03。這份文件記錄需求訪談與設計判斷，供檢視和接續工作。它不是已完成教材的驗收報告；第一輪訪談已完成；學習目標與起點已可整理，教學方案仍需由連續教材驗證。

## 這個專案要解決什麼

學習者是新人工程師，大學修過相關課程，但目前多數通訊與系統概念無法自行串起來。例如對IP的理解主要停在「網路中的門牌」；聽過課程或名詞不能當成已有可運用的基礎。

產品目標是幫助學習者從這個起點建立原理與正常流程的理解，再逐步具備閱讀公司程式、分析故障與修正既有程式的能力。遇到流程停止或不正常時，能說出可能出問題的環節、提出理由、選擇查證方式，並在修正後檢查原功能及相關功能。

「中級」在此用能力描述，不用工程職稱作保證。教材要涵蓋走到這些能力所需的知識；常見問題及解答只是應用材料，不能代替課程正文。

目前訪談不要求提供公司原始碼，也不要求先找出某個真實故障。使用者已描述的能力缺口足以確定產品目標；實際公司資料是未來套用知識時的材料。

## 從起點走到目標的能力階段

下面是每個主題可採用的進階關係，不是要求全站主題混成一條課程。

| 階段 | 要建立的能力 | 如何觀察是否學到 |
| --- | --- | --- |
| 認識 | 知道概念在解決什麼問題，能用自己的話解釋。 | 能解釋IP的用途，指出「門牌」比喻可以幫助哪一部分理解、還有哪些事情尚未說明。 |
| 理解關係 | 知道角色、資料與設定如何配合，能重述正常流程。 | 能畫出一次通訊的主要步驟，說明每一步接收什麼、做什麼、交給誰。 |
| 推理 | 根據原理預測換一項條件後會發生什麼。 | 換成不同目的地、資料格式或等待條件時，能沿著已學的流程解釋影響。 |
| 閱讀實作 | 把文件、設定、程式及工具觀察放回概念模型。 | 能辨認哪段程式建立資料、啟動工作、等待結果及更新狀態；不必先背整個SDK。 |
| 維護 | 提出故障候選、選擇能區分原因的查證，進行有理由的有限修正。 | 能說明懷疑某環節的原因、下一個檢查及修正後需要驗證什麼。 |

「流程當機」先視為工作情境的描述，不直接等同某個技術原因。後續課程會教如何分清程序退出、畫面無回應、工作等待及結果未顯示，並從各自正常運作推導候選原因。

## 初步調查發現與修正方向

調查已抽讀網路、Ozeki、PTT、作業系統及DSP的代表章開頭與段落安排，另檢查路由、並行章和呈現程式。這不是全站逐句內容審查。

| 現有問題 | 實際例子 | 設計判斷 |
| --- | --- | --- |
| 正文太快增加新概念 | 網路第一篇很快要求理解事件處理、封裝、ASCII／HEX、解析器與傳輸結果。 | 先安排概念需要的前文，把概觀、資料表示、網路交付及程式追讀逐步展開。 |
| 短定義被當成已教會 | IP章短時間內加入介面、來源選址、監聽、雙協定及TCP狀態。 | 新概念要有原因、具體例子與推導；一句定義不能作為下一個複雜推論的唯一前置。 |
| 基礎與深入議題放在同一篇 | DSP開頭由樣本、三角函數、複數一路跳到DFT、窗及尺度。 | 根據理解步驟拆分，數學需要在使用前教，深入內容有清楚進階入口。 |
| 固定模板控制正文 | 每章要求相同例題、追碼、故障及題數配額。 | 內容按概念的教學需要安排；有些章先只教原理，有些章適合讀碼，有些章再整合診斷。 |
| 技術驗證代替學習驗收 | 模型、答案、連結與發布一致，即被當作教材完整。 | 技術正確性與學習可理解性分開驗收；兩者都需要，且不能相互代替。 |
| 首頁面資訊遮住教學開場 | 正文前有目標、下載、前置與整段時間安排。 | 開場先交代本章問題、和前文的關係及要理解的核心。其他資訊按需要呈現。 |

現有圖、技術例子與模型可能可重用，但需要重新放到合適的教學位置。現有123篇是素材盤點，不是新課程必須維持的篇數或切分方式。篇幅由概念展開、必要前置和解釋過程決定，避免先指定字數再填內容。

## 教材正文如何寫

正文應讓讀者沿著一個連續問題逐步理解。例如先看到兩個程式為什麼需要交換資料，接著理解要交換什麼、資料如何表示、如何交付，再逐步認識相關協定和程式介面。圖與例子要跟著解說逐步增加元素，不能一次展示完整工程圖再要求初學者自行拆解。

名詞在正文需要它時引入：先說它解決的問題，給白話意思及正式名稱，再用例子展開。本章只會在後文使用的深入概念可以先做簡短路標，交代稍後會學；不必為了「所有名詞都定義」在開頭塞完整名詞表。前置查閱入口也不能代替正文必要的銜接。

比喻可用來入門，但必須逐步接回實際機制。例如「IP像門牌」之後要讓讀者知道位址用在哪個動作、由誰使用、如何配合其他資訊，才能支援後面的推理。

練習先確認理解及解釋，再逐步增加新條件、讀碼及故障分析。不要求每個基礎章立刻做公司故障定位，也不把正文改成練習答案的摘要。

先以網路入門作試寫，因目前起點已有明確依據，且它能支持後續Socket、Wireshark與VoIP。這組試讀不強制變成全站共同入口，其他主題仍獨立。

| 新版篇章 | 主要教學問題 | 與前文的銜接 |
| --- | --- | --- |
| 兩個程式為什麼需要通訊 | 使用者操作、兩端角色、請求與回覆分別是什麼？ | 用可理解的日常任務建立角色及正常順序。 |
| 要交換的資料如何表示 | 文字與數值如何表示成byte，如何讀值及長度？ | 沿同一份READY回覆教bit／byte、ASCII、進位記法、HEX、UTF-8與文字數字。 |

## 工作方式與驗收

產品規劃負責確認學習終點和取捨；課程設計負責知識先後；教材撰寫負責連續解說；技術審查負責原理與例子正確；讀者角度審查負責檢查依靠前文是否讀得懂；網站工程負責呈現和維護。這些是不同責任，不代表需要同時開六個代理。不同作者若共享錯誤規格，仍會產生相同問題。

讀者角度審查從本篇被允許的前置出發：逐段問「這句推論用了哪些知識、前面是否教了、我是否知道為什麼進到這一段」。技術專家熟悉名詞不能代替這項檢查。

使用者主要檢視理解、節奏與方向，不需要替製作者設計課綱。試寫後用解釋、流程重述和小幅條件變化觀察學習；若讀不懂，要查明是正文缺橋梁、起點判斷錯誤、呈現問題或其他原因，不能直接怪讀者，也不能每次都只加一個QA。

教學方法參考[IES教學安排指南](https://ies.ed.gov/ncee/wwc/PracticeGuide/1)的圖文整合、具體與抽象連結、示範與練習安排。這是設計依據，不是此專案學習效果的證明。

## 本次結果、限制與下一步

第一輪三項訪談與硬體深度補充已完成，學習終點、起點與入口方式已有明確依據。新的教學方案覆蓋16個獨立主題及可選共同基礎；硬體深度已按軟體維護目的調整。三篇連續網路入門已完成，網站另設新版入口與閱讀順序，其餘123篇明示舊版參考、待重編。

作者與另一位審查者全文閱讀，整合方親自連讀三篇及練習、檢查圖文，並處理故事一致、前置依賴、進位用途及本地網路措辭。具體發現、修正及驗證界線見[整合審查](reader-review.md)。網站與資料檢查均通過，數值及SVG已核對；手機、桌面圖表已人工檢視。結構清單和瀏覽器報告只保存證據，不作學習品質的替代。

目標讀者尚未完成實際試讀，因此這次只能說教材已具備連續解說及自身前置，不能說已證明使用者學會或已完成全站重製。下一步以這組試讀觀察能否說明角色、數值表示與正常來回，再修正剩餘薄弱處；後續展開目的地址、交付與程式閱讀，各獨立主題按同一教學原則重編。
