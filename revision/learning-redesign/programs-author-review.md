# 第1篇作者自審：兩個程式為什麼需要通訊

本篇是三篇連續試讀的入口，寫給網路概念主要停在 IP「門牌」比喻、稍懂 if／else 及迴圈的新人工程師。本文實際推理不需要 IP、進位換算或 C#；條件判斷只用來幫助想像 B 收到內容後選擇處理。自審時間：2026-10-03。

## 正文要讓讀者建立什麼

讀者先認識小安需要答案，而資料已存在 B 的程式裡，再把這個需要分成 A 與 B 的工作。接著把「問一下」展開成 STATUS? 請求與 READY 回覆，教共同約定如何使兩邊的處理配合。最後走完 B 的處理、回覆到 A、A 顯示的正常順序。後段用少量異常推演，讓讀者看到正常順序能支持什麼思考，不把故障當成全文骨架。

本篇的完成標準是：讀者能說出資料與畫面分別在哪個程式，解釋訊息兩個方向與用途，重述正常步驟，並說明收到回覆後為什麼還需要更新畫面。五道練習皆可從已教內容回答，不要求程式操作或未教工具。

## 每節如何累積

| 節 | 起步知識與新增內容 | 下一節為什麼接得上 |
| --- | --- | --- |
| 1 從小安想知道的一件事開始 | 從一般軟體操作起步，交代畫面在 A、資料已在 B，因此要交換資訊；此時才命名「通訊」。 | 知道要合作後，自然追問「各自做什麼」。 |
| 2 把人的目的分成兩個程式的工作 | 分開人、電腦與程式；先講工作，再介紹用戶端與伺服器端角色。 | 角色已知，可以把人的操作轉成另一個程式要處理的具體要求。 |
| 3 查詢按鈕要變成一個具體問題 | 引入 STATUS?、READY；先給用途，再介紹訊息、請求與回覆；分清已保存資料、回覆與畫面結果。 | 內容已有，但其意思尚未自動成立，接著問程式如何認得它。 |
| 4 共同約定讓相同文字有相同意思 | 先用兩位作者不同寫法展示合作需要，再給完整小約定並命名協定；限制為一次一筆查詢。 | 規則已教，下一節才能據此推演 B 收到要求後的處理。 |
| 5 B 收到問題後還要做哪些工作 | 依序教認出要求、讀資料、建立回覆；BUSY 變化在說明其約定後才使用。 | B 已備妥答案，便能回到 A 接回整件工作。 |
| 6 把一次正常查詢從頭接到畫面 | 把先前各步接起來，教 A 理解回覆與顯示的責任，用垂直圖重述。 | 正常工作完整後，才有依據看「缺少最後結果」時能想到哪些位置。 |
| 7 用已學的順序理解還沒看到答案 | 只依已學工作提出前段與後段候選；以已知 A 收到 READY 縮小後續查看方向。 | 結尾接下一篇：字元如何成為電腦能處理的資料。 |

小停頓只安排在協定教完後，讓讀者以改變寫法確認「程式依共同規則認出要求」。後面五題依序確認角色、訊息用途、順序、狀態值變化與流程推理。解答列出思考步驟，不只給答案。

## 原理來源核對

實際讀過以下官方頁面；本篇例子與教學解說自行撰寫。來源用於核對原理，正文不要求讀者開外鏈補缺。

- [Microsoft：Interprocess communications](https://learn.microsoft.com/en-us/windows/win32/ipc/interprocess-communications)：開頭明說應用之間交換與分享資料可以支持專業分工，並定義 client 要求服務、server 回應要求。第1、2節依此核對用途與角色。本文沒有把 server 當作電腦硬體種類，也沒有推定所有通訊都採這個模式。
- [NIST：protocol](https://csrc.nist.gov/glossary/term/protocol)：核對協定包含系統間合作的規則、格式與程序。第4節以雙方認得的要求、相應工作、答案寫法與一次一筆順序建立小約定，符合這個意義；沒有宣稱這就是完整網路協定。
另曾核對 IETF RFC 9110 §3.3–3.4 的請求與回覆結構，但它是 HTTP 的規格，而本篇使用自設約定，對讀者沒有直接補充作用。依主代理讀者審查建議，已從教材來源列表刪除，保留上面兩項直接支持本篇原理的來源。

本文的因果順序另依原創示例自身規則檢查：A 要求讀資料；B 認出要求後才能完成此筆讀取與回覆；A 收到並理解後才能顯示此筆結果。BUSY 變化不會改變查詢內容，因為狀態資料與要求讀資料的動作是不同角色。

## 前置與比喻的邊界

正文沒有要求讀者理解 Socket、TCP／UDP、Port、封裝、ASCII／HEX、async、回呼或 SDK，也沒有偷用多查詢配對、最新時間戳、記憶體共享等概念。兩個程式的交付方式先保留為第三篇要打開的步驟；解釋角色與順序時不依賴其實作。

「同事手上有紀錄」只用來引入目的、資料位置與合作。第4節接回程式按規則辦事，說明人能理解多種問法、程式依已寫的處理，避免把人能聽懂意思當作程式自動理解文字的原因。

STATUS? 不帶換行，READY 不帶換行；本篇尚不教授資料表示或訊息邊界。B 的設備狀態已存在，沒有新增真實設備或取得狀態的硬體流程。一次只進行一筆查詢，不要求讀者掌握多筆請求識別。第2、3篇作者已收到這些約定。
