# 第1篇作者對第2篇的新手銜接審查

2026-10-03。審查對象為 `docs/content/lessons/networking--messages-and-bytes.json`。按訪談起點與第1篇已教內容逐節閱讀，沒有修改他人的教材。

## 判斷與依據

第2篇可以接在第1篇後。它從同一份 READY 回覆問「交出去的資料是什麼」，再認識 bit／byte、數值、ASCII 對應、進位記法與 HEX 閱讀，沒有預先要求理解傳输程式。核心推理能由正文跟上：資料大小→字母對應值→不同進位只是同一值的寫法→一列 bytes 的內容與長度→不同文字編碼的長度→讀文件時分清文字與數值。

未發現需要補讀其他教材才能完成的重大跳躍。UTF-8 的中文數值在本篇是明示提供的查表結果，不要求新手從未教的編碼規則推導；本篇的任務是理解多個 bytes 可以共同表示一個字，並算出文字內容的長度。後續數量5的例子有另行宣告，不會讓讀者必須誤認原情境增加了欄位。

## 兩處可改善的小摩擦

1. 第1節第二段「紙上寫 R／螢幕看見 R 的形狀」已說出需要表示規則，但直到第3節才明確看到「字母對應到數字」。新手可能在第2節數 bit 大小時，暫時不明白這和文字有什麼關係。第1節末段若加一句「我們會先看資料怎麼用0和1表示，再看一個字母怎麼對應到一個數值」，會讓接下來的步驟更可預期。原文已有「先認識計量單位再回看R」，因此這是可讀性微調，並非欠缺必要前置。
2. 第8節首句說 B 已有「已準備好」這項狀態資料，第1篇則具體說 B 保存的值是 READY。兩句在意義上可相容，但這套教材正在教「意思／文字／byte」的區別，初學者可能以為 B 原本保存的是中文字，後來另外把它翻譯成 READY。建議寫成「B 已保存的狀態值是 READY；按兩端約定，它表示已準備好」，再沿用原文走進 ASCII。這能保持三篇故事的資料起點一致。

另外，第2節說「空格常用來把不同 byte 分開」，當時只展示一組01010010，尚未真的需要空格。它已有說明要依資料約定，所以不構成錯誤；若要降低開頭密度，可把這句移到第5節 HEX 資料列出現後。這是一項節奏選擇，不是必改缺陷。
